<p>Migrated four connected applications from .NET 9 to .NET 10. The migration itself was mostly mechanical, but three things caused real work: package version conflicts that broke the release pipelines, odd behaviour changes in the backend file conversion code, and starting later than would have been ideal.</p>
<h2>At a glance</h2>
<ul>
<li><strong>Scope</strong>: Four applications moved from .NET 9 to .NET 10.</li>
<li><strong>What broke</strong>: Package versions that failed CI/CD on release builds, and unexpected backend changes around file conversion.</li>
<li><strong>Safety net</strong>: Automated xUnit tests and updated Azure DevOps pipelines.</li>
<li><strong>Outcome</strong>: All four apps migrated and released.</li>
</ul>
<h2>Technical Showcase</h2>
<ul>
<li><strong>Stack</strong>: C#, .NET 10, ASP.NET Core, background services, xUnit</li>
<li><strong>CI/CD</strong>: Azure DevOps build and release pipelines</li>
<li><strong>Role</strong>: Led the migration across the four applications</li>
</ul>
<hr>
<h2>1. The Challenge</h2>
<p>Four applications shared libraries and depended on each other, so they had to move together. A version mismatch in one place could break the others, and the release pipelines had to keep working throughout.</p>
<hr>
<h2>2. What Went Wrong</h2>
<ul>
<li><strong>Package versions broke the release pipelines</strong>: Package version conflicts made CI/CD fail on release builds. The failures only appeared when releasing, not during normal development builds, which made them easy to miss until late.</li>
<li><strong>Backend file conversion behaved differently</strong>: Some backend code that converts files changed behaviour after the upgrade. These changes were odd and needed their own investigation and test coverage.</li>
</ul>
<hr>
<h2>3. What Fixed It</h2>
<ul>
<li><strong>Standardised package versions</strong>: Aligned package versions across all four apps so they stopped diverging.</li>
<li><strong>Updated the pipelines</strong>: Moved the Azure DevOps YAML pipelines to the .NET 10 SDK so that release builds matched what ran locally.</li>
<li><strong>Tests around the risky parts</strong>: Added xUnit coverage for the file conversion paths and service lifecycles, so behaviour changes showed up as failing tests instead of production surprises.</li>
</ul>
<hr>
<h2>4. Results</h2>
<ul>
<li><strong>Four apps migrated</strong> to .NET 10 and released.</li>
<li><strong>Releases working again</strong>: The pipeline failures were resolved by standardising the package versions and updating the pipelines.</li>
</ul>
<hr>
<h2>Lessons</h2>
<ol>
<li><strong>Test the release pipeline early</strong>: Release builds failed in ways that normal builds did not, so run a release build as soon as the first project is upgraded.</li>
<li><strong>Keep package versions in one place</strong>: Version differences between connected apps cause most of the surprises.</li>
<li><strong>Start sooner and keep control of the timing</strong>: With more control over when development started, the migration could have begun earlier and left more room for the unexpected file conversion changes.</li>
</ol>
